# T8 放置ファイル検出 仕様書

対象ブランチ: `t8`（`sub` から分岐） / 優先度: P2
関連: 全体仕様書 6.5・8章、チケット一覧 T8、HANDOFF 5章(A)

状態: **確定・実装済み**（2026-09-17）。相談時に [**要確認**] としていた項目は、すべて下記の内容で決定した。

---

## 1. 目的

分類済みのファイルのうち、長く開かれていないものと、同じ中身が重複しているものを見つけ、
MOFUとの会話の中で「残す」か「ごみ箱へ」かを1件ずつ決めてもらう。

放置ファイルの一覧画面は作らない。検索や分類の通知と同じく、会話ログにカードとして流す（HANDOFF 3章の方針）。

## 2. 範囲

| 含む | 含まない |
|---|---|
| 候補の算出 | 常時監視・定期スキャン（全体仕様書6.5でオンデマンドと決定済み） |
| 片付けタイムの会話の流れとカード | 放置ファイル専用の画面・タブ |
| 「残す」「ごみ箱へ」の処理 | ごみ箱の中身の一覧表示・完全削除 |
| 「残す」を選んだファイルを当面は再提案しない仕組み | 元に戻す（Undo）の本体（T9で実装） |

### チケット一覧との食い違い（決定）

チケット一覧 T8 には「『放置ファイル』タブを開くと」「削除/アーカイブできる」と書かれているが、
HANDOFF の相談結果は「タブは作らない」「残す / ごみ箱へ の二択」になっている。

- HANDOFF の方針を正とし、チケット一覧 T8 の受け入れ条件を本仕様書に合わせて書き換えた
- アーカイブ（別フォルダへ退避して検索対象から外す）は作らない。選択肢が3つになると手が止まるため

## 3. 候補の算出

### 3.1 対象

- `files.status = 'active'` のファイル全件（`db.get_active_files()`）
- 実ファイルが存在しないもの（外で移動・削除されたもの）は候補から外す。DBは変更しない
- 「残す」を選んでから一定期間内のものは外す（5章）

### 3.2 判定材料

| 材料 | 取り方 |
|---|---|
| 未アクセス日数 | 今日 − `last_accessed_at`（分類時に `created_at` で初期化済み） |
| 一度も開いていない | `last_accessed_at == created_at` |
| 重複 | `files.hash` が同じ active なファイルが他にある |

### 3.3 候補にする条件

次の**どちらか**に当てはまるファイルを候補にする。点数による重み付けはしない。

| 条件 | カードに出す理由の例 |
|---|---|
| 未アクセス **30日以上** | 「45日開いてない」 |
| 重複していて、残す側ではない（3.4） | 「『ドット絵イラスト』に同じファイルがある」 |

補足として、当てはまる場合は次の一言も理由に添える（これだけでは候補にならない）。

- 入れてから一度も開いていない →「入れてから一度も開いてない」

並び順:

1. 両方の条件に当てはまるもの
2. 重複だけに当てはまるもの
3. 未アクセスだけに当てはまるもの
4. 同じ順位の中では、未アクセス日数の長い順

ファイルサイズは候補の条件にしない。カードには既存のファイルカードと同じくサイズを表示する。

30日という値は、定数 `STALE_DAYS = 30` として `t8_cleanup.py` の先頭に置く。

### 3.4 重複したときにどれを残すか

同じハッシュのファイルが複数あるとき、次の順で1件を「残す側」に決め、残りを候補にする。

1. `last_accessed_at` が一番新しいもの（実際に使われている方）
2. 同じなら `created_at` が一番古いもの（先に入れた方）

残す側のファイルは重複の条件には当てはまらない。30日以上開いていなければ、未アクセスの条件で候補になる。

作業を始めたPCのDBの例（同じ画像が3件）:

| id | 場所 | last_accessed_at | 結果 |
|---|---|---|---|
| 1 | ドット絵イラスト/n812.png | 9/17 10:05（開いた） | 残す側 |
| 3 | ポケモン/n812_1.png | 9/16（開いていない） | 候補 |
| 4 | ポケモン/n812.png | 9/17 08:11（開いていない） | 候補 |

### 3.5 デモでの見え方

作業を始めたPCのデータは全部ここ数日で入れたものなので、未アクセスの条件にはどれも当たらない。
そのDBで出る候補は重複の2件だけになる。

デモや確認のための仕掛け（日数の条件を縮める設定など）はアプリ側に作らない。
未アクセスの条件を確かめるためのファイルは、実装が終わった後に別途用意する。

## 4. 会話の流れ（片付けタイム）

### 4.1 入口

**MOFUから声をかける。** 候補があれば、吹き出しで「片付けタイムにしない？」と誘う。

- 吹き出しは分類の通知と同じ部品（`Toast`）を使い、ボタンは「はじめる」「またこんど」の2つ
- **同じ内容を会話ログにも流す。** 吹き出しは5秒で消えるので、後から会話パネルを開いても
  ログの「はじめる」から始められるようにする（分類の訂正と同じ考え方）
- 吹き出しの「はじめる」を押すと、会話パネルが開いて4.2の流れに入る
- 「またこんど」または吹き出しが消えたときは何もしない。ログのメッセージはそのまま残る
- ダウンロードの通知を出している間や、分類の処理中は声をかけない。終わってから出す
- 会話パネルが開いているときは吹き出しを出さず、ログにだけ流す

声をかけるタイミング（決定）:

- アプリの起動から1分後に一度だけ候補を算出し、1件以上あれば声をかける。
  その後は起動中、**1日1回まで**（前回声をかけてから24時間たったら、次の分類が終わったタイミングで再度確認する）
- 「またこんど」を押した場合も、次に声をかけるのは24時間後

自分から始める入口（決定）:

- キャラの右クリックメニューとタスクトレイのメニューに「片付けタイム」を足す（声かけを待たずに始めたいとき用）

### 4.2 流れ

声かけ（4.1）の文面は「〇件、片付けられそうなのがあるよ。片付けタイムにしない？」＋「はじめる」「またこんど」とする。

1. 「はじめる」を押した時点で、候補を算出し直す（声かけから時間がたっている場合があるため）
2. 候補が0件なら「いまは片付けるものは無いよ。えらい。」で終わる
3. 右クリックメニューから始めた場合は、声かけを経ていないので、ここで同じ文面と「はじめる」「またこんど」を出す
4. 候補を**1件ずつ**カードで出す
5. カードの「残す」「ごみ箱へ」のどちらかを押すと、そのカードのボタンは消え、結果を一言返して次の候補を出す
6. 全部終わったら結果をまとめて褒める。例:「おつかれさま。［ごみ箱へ 3件 / 残す 1件］ 2.4 MB 片付いた。」

1回で出す件数の上限（決定）:

- 最大5件。残りがあれば、最後に「まだ〇件あるよ。続ける？」と聞く

途中でパネルを閉じた場合は、その回は終わりにする（次に開いたときに続きからは再開しない）。

### 4.3 カード

既存のファイルカード（`FileCard`）と同じ見た目で、次の点だけ変える。

- ボタンは「残す」「ごみ箱へ」の2つだけ。強調（白黒反転）するのは「ごみ箱へ」
- カードの中に、3.3の理由を並べて書く（例:「45日開いてない / 入れてから一度も開いてない」）
- ファイル名を押すと、既存の「開く」と同じく既定アプリで開く（中身を見てから決められるように）

ファイル名を押して開いたときの扱い（決定）。
開くと `last_accessed_at` が更新されるので、次回からはこのファイルは未アクセスの候補に出なくなる。

- それで良しとする（中身を確認した＝使った、とみなす）
- 片付けタイムの途中なので、会話パネルは閉じずに残す（通常のカードの「開く」とはここが違う）

白黒ドット絵のルール（HANDOFF 3章）に従う。色・角丸・影は使わない。

## 5. 「残す」の処理

「残す」を選んだファイルは、しばらく候補に出さない。
そのためにDBへ記録が要る。

`files` テーブルに `kept_at DATETIME`（NULL許容）を追加する。「残す」を押した日時を入れる。

- `kept_at` から **30日** たつまでは候補から外す（定数 `KEEP_DAYS = 30`）
- 30日たった後も、3.3の条件に当てはまれば再び候補になる
- 既存DBには `db._migrate()` で列を足す（`categories.embedding` と同じやり方）
- 全体仕様書 8章のテーブル定義にも追記する

重複で候補になったファイルを「残す」と選んだ場合も、同じく30日間は候補に出さない。

`last_accessed_at` を更新して代用する案は採らない。「開いた」と「残すと決めた」が区別できなくなるため。

## 6. 「ごみ箱へ」の処理

T9（ゴミ箱/Undo）の前提に合わせ、即時削除はしない。

1. `files.status` を `'trashed'` にし、`files.path` を退避先に書き換える
2. `trash_log` に `action_type = 'delete'` と移動前のパスを記録する
3. 実ファイルを退避先へ移す
4. 1と2は `db.mark_trashed()` で1トランザクションにまとめる（T6の保存と同じ形）。
   実ファイルを先に移し、DBの更新に失敗したら実ファイルを元の場所に戻す

`status = 'trashed'` のファイルは、既存の `get_active_files()` の対象外なので、検索にも出なくなる。

実ファイルの移し先（決定: 案A）。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **A. `organized/.trash/` へ移す（採用）** | T9の「元に戻す」が簡単に作れる。追加のライブラリが要らない | ディスクは空かない。ごみ箱を空にする手段が別に要る |
| B. Windowsのごみ箱へ送る（`send2trash`） | 利用者の感覚に合う。ディスクも最終的に空く | アプリから元に戻せない。依存ライブラリが1つ増える |
| C. 実ファイルは動かさない（DBの印だけ） | 一番簡単 | ファイルが残り続け、`organized/` 内で見えてしまう |

- 退避先のファイル名は同名衝突を避けるため `<id>_<元のファイル名>` とする
- `files.path` は退避先に書き換える。元の場所は `trash_log.original_path` に残る
- 4.2の締めの言葉は「〇MB 空いた」ではなく「〇MB 片付いた」とする（実際にはまだディスクは空いていないため）

ごみ箱へ入れた直後の「元に戻す」（決定）:

- T8では出さない。T9で、会話ログの「ごみ箱へ入れたよ [元に戻す]」の形でまとめて作る

## 7. 変更するファイル

| 場所 | 追加するもの |
|---|---|
| `t8_cleanup.py`（新規） | `find_candidates()`：候補を算出し、理由付きで3.3の順に返す<br>`keep_file(file_id)`：「残す」を記録する<br>`trash_file(file_id)`：6章の処理 |
| `db.py` | `kept_at` 列のマイグレーション、`set_kept()`、`mark_trashed()` |
| `ui_kohaku.py` | 声かけ（吹き出しと会話ログ）、右クリックメニューの入口、片付けタイムの会話の進行、候補カード |
| 全体仕様書・チケット一覧・HANDOFF | 本仕様書で決まった内容を反映する |

- SQLiteへのアクセスは全て `db.py` に置く（HANDOFF 4章の約束）
- DBファイルのパスは `db.DB_PATH` だけを使う
- `find_candidates()` は重いモデルを使わないので、会話パネルからそのまま呼んでよい（別スレッド不要）

`find_candidates()` の戻り値の形:

```python
@dataclass
class Candidate:
    file: dict            # db.get_file() と同じ形
    stale_days: int       # 未アクセス日数
    duplicate: bool       # 重複の条件に当てはまるか
    reasons: list[str]    # カードにそのまま出す文言
```

## 8. 受け入れ条件

- [ ] 候補があるとき、MOFUが吹き出しで片付けタイムに誘い、同じ内容が会話ログにも残る
- [ ] 吹き出しが消えた後も、会話ログから片付けタイムを始められる
- [ ] 片付けタイムを始めると、その場で候補が算出される
- [ ] 30日以上開いていないファイルと、重複の残す側でないファイルだけが候補になり、3.3の順に並ぶ
- [ ] カードに、候補になった理由が全て書かれている
- [ ] 同じハッシュのファイルが複数あるとき、3.4の順で1件が残り、他が候補になる
- [ ] 「残す」を押したファイルは、30日間は片付けタイムに出てこない
- [ ] 「ごみ箱へ」を押すと、`status` が `trashed` になり、`trash_log` に記録され、実ファイルが退避先に移る
- [ ] ごみ箱へ入れたファイルは検索に出てこない
- [ ] 実ファイルが無くなっているものは候補に出ず、エラーにもならない
- [ ] 候補が0件のとき、その旨を返して終わる
- [ ] UIが白黒ドット絵のルールに従っている

## 9. 動作確認の手順

同じ画像を3回入れ、そのうち1件をアプリから開いたDBで確認できる範囲
（別のPCでのデータの作り方は HANDOFF 5章(A)）:

1. 起動して1分ほど待つ → 吹き出しで「2件 片付けられそうなのがあるよ。片付けタイムにしない？」と誘われる
   （id 3・4）。パネルを開くと会話ログにも同じ内容が残っている
2. 吹き出しかログの「はじめる」→ 候補のカードが1件出る
3. カードの理由に「『ドット絵イラスト』に同じファイルがある / 入れてから一度も開いてない」と出る
4. 1件目で「残す」→ 次のカードが出る
5. 2件目で「ごみ箱へ」→ 終わりのまとめ「ごみ箱へ 1件 / 残す 1件」が出る
6. 右クリックの「片付けタイム」→ 「いまは片付けるものは無いよ」と出る（1件は残した、1件はごみ箱の中）
7. 「ポケモン」で検索 → ごみ箱へ入れたファイルが出てこない
8. `organized/.trash/` に `<id>_<ファイル名>` で退避されている

未アクセスの条件は、実装後に用意するファイルで確認する（3.5）。
